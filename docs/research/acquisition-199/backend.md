It requires exact original prospect/email/campaign identity, six business/contact/jurisdiction/provider/history/binding gates, a confirmed exact niche and receipt, two registered Component Studio refs and approved immutable review hashes. Candidate references fail closed. Approved HTML is frozen into recipe_snapshot; later room reads require no campaign filesystem. GET `/api/acquisition/samples/{64hex}` returns `{schema:'famtastic.acquisition-sample.v1',illustrative:true,niche,business_name,bindings,recipes:[{id,version,title,summary,sha256,preview_path}],preference,registration_path}`. GET the preview_path returns frozen bound HTML with sandbox CSP. Both responses are private/no-store/no-referrer/noindex. Repeated room GET does not create events, accounts, preferences, jobs or proofs. Expiry/revocation denies public room access.

POST `/api/acquisition/samples/{64hex}/preference` accepts JSON `{recipe_id}` with same-origin/Fetch-Metadata checks; only one of that invitation's two recipe IDs is valid. POST `/api/acquisition/samples/{64hex}/claim` requires authenticated Drupal session and `X-CSRF-Token` from the native session response. The verified customer's email must match the original invitation. Login/register reuse native routes; registration input `sample_continuation` validates before User insert hooks and binds a server-side pending account. Verification on another device can claim that pending account without the room secret. Expired/revoked rooms preserve the already-bound verified account's saved context.

Session/verification responses expose `continuation: {kind:'acquisition_sample',context_id:32hex,request_public_id:null|string,niche,recipe_id:null|string,return_path:'/portal?start=website&section=projects'}`. An explicitly sample-originated new website request supplies `acquisition_context_id`; server intake receives invitation/niche/advisory preference with `formal_proof_selection:false`. `famtastic_acquisition_request` binds invitation to exactly that request_id, customer_id and distinct request_prospect_id. Reuse returns the associated request through continuation; it never attributes every later customer purchase to the sample. Report joins native request/Commerce authority through this exact mapping. Purchase suppression also recognizes the verified claimed customer and mapped request prospect even when the account's generic prospect differs.
