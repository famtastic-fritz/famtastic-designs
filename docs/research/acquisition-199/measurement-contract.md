# Acquisition native report contract

Staff GET `/api/acquisition/report/{campaign_key}` returns aggregate schema `famtastic.acquisition-report.v1`. The route requires `administer famtastic pipeline`; JSON is private/no-store and has no contact names, addresses, account IDs, invitation bearer links or tokens. Root frontend owns the staff page. The report reads only; it cannot send, charge, generate or deploy.

Source reconciliation: `CampaignMessageService::track()` already records once per open/click event key and stamps native message rows. `EmailEventController` already supplies opaque tracking and signed provider endpoints. `MarketingCommandController` already joins campaign/prospect/request to Commerce fulfillment. `PipelineAnalyticsService` still references legacy `famtastic_order` and package amounts: this acquisition report deliberately reads current Commerce payment entities and does not extend that legacy calculation.

Population comes from the exact campaign's sample invitations; explicit eligibility receipts count qualification separately from invitation issuance. Native sample message rows retain campaign and immutable message-key identity. Sends, opens and clicks count distinct message rows; opens/clicks include unclassified scanner/privacy activity. Confirmed preference/verified claim events are separate meaningful actions. Incoming reply receipt is raw evidence with unknown machine status; only explicit human reply events count human replies. Missing campaign-attributed replies remain unknown, not a false zero.

Verified registrations join invited prospects to verified customer records. The portal creates a distinct commercial prospect. Immutable famtastic_acquisition_request mappings bind only its exact request/customer/prospect to the original invitation. Submitted mapped authenticated website requests count completed interviews; unrelated same-customer purchases are excluded. Payment association joins those exact mapped request/prospect records to actual Commerce order IDs, including fulfillment records in refunded/cancelled state. Payment amounts/refunded amounts and state come from current Commerce payment entities; fulfillment/order/catalog amount snapshots are not revenue authority.

Capture identity is gateway + payment mode + provider capture ID (entity ID fallback); repeated identical receipts deduplicate. Conflicting repeated receipts, unsupported currency or malformed refund amounts withhold financial totals. Partial/full refunds reduce revenue, voids/authorizations/failed payments add none. Only positive live-mode captured payments count paid customers; zero-dollar sponsorship adds no paid customer or revenue. Test-mode totals are isolated in `controlled_sandbox` and never contribute to campaign totals. No actual payment was executed.

Breakdowns: niche, frozen message content ID, explicit preferred sample, experiment arm. Message day and invitation identity are validated against native metadata. A repeated invitation for the same prospect is deduplicated per niche/arm for funnel and monetary counts. Preferred-sample and message purchase causality is not available from existing immutable evidence, so their financial metrics remain unknown. A preference is not customer formal proof selection. Known campaign spending is separate from complete measured provider/processing/fulfillment/labor costs; total costs/contribution stay unknown until receipts support them. The report does not infer a conversion lift or launch turnaround from raw interactions.

Synthetic proof: `php scripts/acquisition-report-test.php` covers payment replay, conflicting receipts, partial/full refund authority, unrelated-order isolation, unavailable authority, unsupported currency, authorization exclusion, test/live separation, zero-dollar sponsorship, exact decimal conversion, private JSON exclusion, verified/interview joins and meaningful-vs-recorded interactions. Local/source proof is not hosted current-count or owner acceptance evidence. Review classification for this lane is `changed`; deployment and owner acceptance remain pending.

Their outcomes remain visible only as controlled_sandbox.messaging with counts_toward_campaign=false. Unknown provider rows remain recorded native outcomes; they do not prove delivery. The remaining invitation/preference/claim population uses native source records; no test dataset provenance is inferred from an address alone.
